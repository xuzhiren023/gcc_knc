# Review of PhiWeather's first instrumented PGO attempt

**Verdict:** the corrected GCC 5.1.1 collection/use pipeline is credible and useful engineering work. It does not yet establish a WRF speedup or numerical acceptance. The ticket's early 4.489 versus 4.471 s/step is a 0.40% time reduction from one pair, below the write-up's 0.023 s/step noise heuristic. Neither a benefit nor equivalence has been demonstrated. Retain the pipeline; qualify the numerical gate and measure a fixed, balanced block before expanding the experiment.

## 1. Is the method sound?

**Collection and build identity: yes, with a bounded interpretation of the gate.** Replaying the control recipes, changing only 17 members, retaining one libgomp, and using the linked instrumented objects as the reference are appropriate. `build_gen.py:31-50,91-118` checks replay and archive membership. The non-public function-id dependency on the output path is a substantive finding: the old separate-directory gcno reference and separate-directory use build were wrong for 88 local functions. Restoring the instrumented `-o` path fixes the identified loss, rather than suppressing mismatch diagnostics. [R sections 2, 8; L sections 2, 6; P `object_gcov.py:49-84`, `pgo_use.py:184-206`.]

Removing `-w`, rejecting mismatch/missing-data diagnostics, and comparing function identity and arc shape are essential. However, the implementation is narrower than the prose's "every function" guarantee: `gate_gcda` filters to nonzero-arc functions, validates their ident/line/CFG/arc metadata, and does not validate all value-counter shapes. Merged files skip stamp and run-count comparison; the normal multi-input route first checks each original file, making that defensible. Bare `--merged` cannot establish original rank completeness and should not be used for a qualified candidate without those original checks. [P `pgo_use.py:93-155,254-286`.]

The postcompile gate rejects diagnostic markers and forbidden instructions, but **records rather than enforces** positive execution-count notes or a changed object (`pgo_use.py:205-219,293-299`). Changed code alone is not proof of profile consumption: profile-use enables optimizations even without useful counts. The reported 688 notes and wrong-path experiment support this build; they do not prove every function consumed feedback. Require explicit consumption evidence for important hot functions, with reasoned exceptions for unchanged functions, rather than mandating that every object change. [R section 8; L section 6.]

**Threads and ranks: a sensible GCC 5 workaround, not representative production timing.** Single-thread ranks avoid concurrent non-atomic updates in instrumented code. Separate MPI address spaces plus libgcov's exit-time file locking permit a shared flat output directory. Normal completion, unique run directories, all expected files, rank-count summaries and profiling diagnostics matter together; a run count alone cannot rule out stale/repeated contributors. The patched supervisor and both `OMP_NUM_THREADS` and `OMP_THREAD_LIMIT` enforce one thread. [L sections 3-4; P `make_pgo_plans.py:129-161`.]

Direct binary-record inspection found:

| Retained source under CM (each `native/collected/*.gcda`) | Layout in its plan | Files / bytes | PROGRAM_SUMMARY runs in every file |
|---|---|---:|---:|
| `bt-20240720-OKC-HNRLHD6S-PGOTRAIN-02` | 8 x 1, patches 2x4, tiles 5x3 | 17 / 367,456 | 8 |
| `bt-20240619-HOU-HNRLHD6S-PGOT16C2-4x4-02` | 16 x 1, patches 4x4, tiles 2x3 | 17 / 366,096 | 16 |

Each set contains 500 function records and arc, time and value-counter records. This confirms retained profile structure, not scientific correctness or full consumption. R section 8 reports completed training, 1,707/1,374 s integration and Houston's 2.99 GiB minimum free memory. These are different cases and decompositions: their time ratio does **not** isolate rank scaling or instrumentation overhead. L section 9.5's inferred per-rank efficiency is consequently not an identified measurement.

The 4x4 Houston layout obeys WRF's 10-cell minimum patch; the rejected 2x8 layout does not. Memory also constrains ranks. Two ranks per core is a reasonable measured-placement choice for their workload, not a reason to assume identical profiles. Production is 8 x 15 with 2x4 patches and 5x3 tiles; OKC training preserves those spatial loops, whereas Houston's mean inner trip count rises from 7.52 to 9.40 (+25%). Peeling, unrolling, entry/exit frequencies, halo/edge work and hand-kernel fallback selection can all change. [R section 3; L sections 9.1-9.3.]

**Merging: compatible, but not mathematically equal case weighting.** The matching gcov-tool is preferable to custom counter arithmetic, including for value histograms. Gating each original with its own rank count and then re-gating the merge is sound. Default merging sums arc counts; it does not divide by rank count or normalize each case. Whole-domain per-column work may contribute similarly over 60 steps, but per-rank initialization doubles, tile-call counts change, and weather-dependent work differs. Thus "each input weighs one case" in R section 3 and L section 9.7 is only an approximation for some counters. Do not blindly divide the 16-rank profile by two: that would underweight its domain work. Choose workload weights deliberately if needed, using separate-case diagnostics first. [P `pgo_use.py:133-155`.]

**Representativeness is the main unresolved risk.** Both cases cover convective first hours; neither covers a quiet regime or a full diurnal evolution. Training includes startup and all 60 steps, while the proposed timing statistic excludes steps 1-10. That can overweight initialization and early adjustment relative to steady integration. Longer representative training, or a carefully validated steady-state collection window, would help; do not assume that deleting warm-up timing also removes warm-up counters. Instrumentation itself changes inlining and x87 spill/rounding behavior, so evolving branch frequencies need not exactly match production. [L sections 1, 8, 9.7, 10.]

The existing OKC-trained versus Houston-trained comparison confounds weather and decomposition. Evaluate both single-input images and the merge on held-out inputs at the **same production layout**. If decomposition sensitivity must be diagnosed, collect the same weather case with the 8-rank and 16-rank designs and compare per-function normalized arcs plus absolute entry counts. A THM spread of 0.0155 K does not prove no threshold flips: distance to each branch threshold matters. L section 9.3 explicitly labels that argument as belief, not measurement.

## 2. Why little gain, and what could make PGO useful?

**Near-zero gain is plausible even with correct feedback.** The 17-member selection is defensible: 15 members cover 44.3% of the critical-path extent attributed to GCC code, plus RRTMG SW and `solve_em`. That denominator is not 44.3% of whole-program wall time. Hand-written IMCI, MPI/imbalance, I/O and other objects remain outside the optimized set. No evidence here apportions the early timing pair's wall time well enough to assign one cause. [R section 2; P `pgo_common.py:33-38`.]

WRF's regular floating-point loops often offer predictable loop branches, dependencies and memory traffic rather than uncertain dispatch. PGO cannot remove those bottlenecks merely by learning that a loop is hot. Potentially vectorizable loops are not necessarily vectorized in this image: explicit `-fno-tree-vectorize` stays in the recipes. Existing hand-IMCI bodies also do not acquire new SIMD through this PGO rebuild. Physics threshold branches remain possible opportunities; verify their dynamic share instead of declaring WRF branch-free. [L sections 1.2-1.3, 9.3.]

The real use build does substantial work: hot object bytes grow 26.8%, total image text grows 1.2%, and static call-site deltas include +694 memset and +182 memcpy. Counts of call sites are **not** executed call counts. Inlining/unrolling may save overhead but increase instruction footprint, register pressure and x87 spills; the re-enabled loop-pattern pass may move costs into memory helpers. These are credible cancellation mechanisms to diagnose, not measured explanations of the 0.40% pair. [R section 8; L section 8.]

The relevant levers, in order of evidential value:

1. **Use the existing restricted-flags twin to isolate aggressiveness.** It reduces total text relative to control, whereas the full candidate grows it. It is not literally layout-only: its flag list does not disable every non-layout pass, and 271 of 484 function FP censuses still differ. Compare dynamic hot functions, spills, call paths and helper traffic; retain the same numerical gate. [L sections 1.4, 8; P `pgo_use.py:32-34`.]
2. **Inspect placement before adding flags.** GCC 5 already has `-freorder-functions` and `-freorder-blocks-and-partition`: the former groups hot/cold functions for the linker; the latter splits hot/cold blocks subject to target/function restrictions. Check emitted sections and final map, because another flag may merely request an already enabled pass. Distinguish these from first-execution-order `-fprofile-reorder-functions`, already enabled here. Locality can help a large instruction footprint, but cannot create useful branch information. [L section 1; [GCC 5.1 optimization manual](https://gcc.gnu.org/onlinedocs/gcc-5.1.0/gcc/Optimize-Options.html), entries for those options.]
3. **Value profiling is already present.** Counter records exist in both retained sets; L section 1.2 describes division/modulo and indirect-call profiling. Seek profitable dynamic values or indirect targets and resulting specialized code; adding `-fprofile-values` again is not a new experiment. Lean arc-only training may lower collection cost if those opportunities are absent, but requires a consistent rebuilt training/use experiment. It is not a performance conclusion from the current profiles.
4. **Improve coverage before broadening instrumentation.** Prioritize objects containing expensive, profile-sensitive hot functions and their small callees; avoid profiling all 538 eligible members by default. Keep untrained optional physics on normal optimization if GCC 5 would size-optimize useful unexecuted paths. `-fprofile-partial-training` in modern GCC instead ignores feedback for completely unexecuted functions, trading larger code for safer transfer; it does not fix biased counts inside executed functions. It is absent from the GCC 5.1 option set, not a flag to add to this driver. [R section 2; [GCC 5.1 option summary](https://gcc.gnu.org/onlinedocs/gcc-5.1.0/gcc/Option-Summary.html); [current GCC manual](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-fprofile-partial-training).]
5. **PGO plus LTO is possible in principle, but qualify the installed route first.** The read-only command `.tools/knc-bootstrap/cross/bin/k1om-mpss-linux-gfortran.exe -v` reports 5.1.1 and an LTO wrapper; `cross/libexec/gcc/k1om-mpss-linux/5.1.1/` contains `lto1.exe`, `lto-wrapper.exe` and `cyglto_plugin-0.dll`. Thus LTO components are installed; no WRF LTO link was demonstrated here. GCC 5 supports compiling and linking with `-flto` and plugin-aware archive tools. Native-only/hand-assembly objects remain opaque to interprocedural optimization. Qualify a small Fortran/archive/OpenMP link, then compare LTO alone with LTO+PGO using freshly matched training. Do not simply append `-flto` to the existing final link. [Read-only installation query; [GCC 5.1 manual](https://gcc.gnu.org/onlinedocs/gcc-5.1.0/gcc/Optimize-Options.html), `-flto`, `-fuse-linker-plugin`, `-ffat-lto-objects`.]

GCC 5 is a constraint, not an explanation proved by this experiment. It already provides the important branch/value/layout/inlining mechanisms. GCC 16 offers a different optimizer and KNC backend plus newer profile handling, but no controlled same-WRF comparison establishes a version benefit. Atomic profile updates can remove the single-thread training workaround, subject to target support and runtime cost; partial-training and missing-profile diagnostics improve robustness. These are methodological advantages, not a predicted 20% WRF gain. [L sections 4, 12; [GCC instrumentation manual](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html#index-fprofile-update); [GCC optimization manual](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-fprofile-use).]

## 3. Is the non-bitwise tolerance gate reasonable?

**Yes as a staged screen; not yet as a calibrated acceptance claim.** PGO can alter x87 rounding through spills without enabling fast-math. The FP census supports treating these images as potentially non-bitwise; changed assembly does not itself prove changed outputs. THM perturbations that survive input storage, fixed seeds, early-time growth, bias/conservation, finite/completion checks, three identical candidate repeats and separate observation skill are appropriate safeguards. One initial-state perturbation ensemble is an empirical proxy for changed arithmetic at every step, not a general equivalence theorem. [L section 8; T sections 2-7.]

Specific corrections needed before freezing:

- **Calibration uncertainty:** T section 3.3 line 81's `3/270` confidence bound is not justified. Those 270 leave-one-out comparisons share five members, fields, times and the same control; they are not independent Bernoulli trials, even for a claim labelled "per cell." Calibrating a maximum on the four OKC members and then accepting those same members also cannot demonstrate a 5% screen-level false-rejection rate. Use genuinely held-out controls or nested calibration, report the small number of independent members, and describe residual uncertainty. Do not claim 95% statistical indistinguishability from this envelope rule.
- **Zero spread:** T section 3.3 line 65 skips an identically zero control field, conflicting with its nonzero-candidate/zero-spread failure rule and section 6. A new spurious rain/species field must not vanish through the skip. Check structure, finite values and zero-spread differences first; skip a zero field only when the candidate also agrees under the frozen rule. Define zero denominators in Rule B explicitly.
- **Power and multiplicity:** k=1.25 was motivated by quiet Mentor fields, not OKC rain. Complete Rule C calibration and the injected-fault/amplitude-ladder checks before judging PGO. A field with k above 2 is "low power," not a pass or permission to omit a required field. Count the actual field/domain/time family and report failures without averaging them away. Four members cannot tightly estimate extreme tails. [T sections 3.3-3.4, 7.]
- **Cadence:** the existing 17-file plans lack early 3-D growth. The suggested S2 cadence starts at step 10 for 3-D fields, so Rule D's step-5 requirement is not available for those fields either. Specify which fields are required at step 5 and collect them, or freeze an explicitly narrower screen. Use identical output cadence in C, C' and T; extra I/O also changes the timing experiment. The current A/B generator still describes the 17-file plan. [T sections 3.2-3.3; P `make_pgo_ab_plans.py:49-58,90-110`.]
- **PGO engagement:** use actual profile-use consumption plus sampled execution of affected hot functions. Kernel-decline counters suit new hand-written SIMD kernels, not a generic PGO transformation. Require same-layout T repeats; tile/thread invariance applies where the control and algorithm establish it, rather than assuming all decompositions must be bit-identical. [T sections 3.3 Rule E, 3.5; R section 8.]
- **Long forecast:** tier b's three or four control-family scores give a very uncertain prediction interval and require distribution/exchangeability assumptions. Use the exact quantile, actual number of metrics and the prediction factor `sqrt(1+1/n)` consistently; the "three flagged metrics" rule also needs calibration. A broad interval including T means no detected gross change, not skill equivalence. Retain the independent release holdout and original-reference comparison. [T sections 4-5.]

The current source explicitly leaves the OKC calibration, bias multiplier and long-run score spread open (T section 7). None of those unrun gates becomes a pass because compilation, profile metadata or deterministic repeats succeeded.

## 5. Can the measurement detect 1-2%?

The early difference is **0.018 s/step**, versus 0.0449/0.0898 s for 1%/2% at the quoted control time. The inherited 0.023 s heuristic is about 0.51%, but a historical repeat spread is not a confidence interval or the variance of paired launches. One pair supplies no estimate of that variance. `C T C T T` is an exploratory screen with unbalanced order and an unbracketed last T, not a sufficient precision study. [Ticket early pair; L section 10; R section 4; P `make_pgo_ab_plans.py:49-64`.]

[ADR-0010 amendment 2, points 1-7](../adr/0010-knc-measurement-protocol.md#amendment-2-2026-11-06-spread-is-a-flag-decisions-use-confidence-bounds) is the relevant rule, superseding rejection for high spread. Its tuning design requires same-process/same-buffer interleaved rounds (at least five), at least three launches, all samples retained, per-round ratios and a bootstrap 95% interval; the near endpoint must beat the predeclared minimum effect. Sign changes across launches mean placement dependence, and effects below 2% require opposite link order. The older "five launches, every launch passes" shorthand is incomplete.

Full WRF images cannot simply be run in that same-process microbenchmark harness. An explicitly labelled **application-level adaptation**, not literal ADR compliance, would be:

1. Freeze one primary statistic (canonical non-I/O d01 mean over steps 11-60), input, production ranks/threads/tiles, sampler policy, output cadence, clock policy and exclusion rules. Keep median, all-step mean and whole integration makespan as secondary diagnostics. Exclude startup identically by fixed step, not by looking for favorable timings. Use exclusive coordinated card windows and keep all valid launches, including regime steps.
2. Use adjacent independent C/T launch pairs, balancing CT and TC in blocks such as `C T T C`, with block orientation randomized ahead of time. Put perturbation/calibration jobs outside the timing blocks. Record each pair's ratio and chronology; resample pairs/blocks, not individual model steps as independent replications. Weather steps are correlated and change workload over time.
3. Start with **five pilot pairs (ten launches)** to estimate paired log-ratio SD. Then freeze a new confirmatory block: **ten pairs (twenty launches)** is a reasonable starting budget if paired SD is around 1%; about **forty pairs** if it is around 2% and detecting 1% is essential. These are planning numbers, not guarantees. If cost is unjustified for a sub-1% result, stop with "benefit not resolved" rather than "PGO cannot help."

For orientation, a two-sided 5% test with roughly 80% power needs approximately
`n_pairs = (1.96 + 0.84)^2 * (s / delta)^2`, where s is the SD of independent paired log ratios and delta the target log-time reduction. Small-sample t inference, drift and correlations can require more:

| Assumed paired SD | Detect 1% versus no change | Detect 2% versus no change |
|---|---:|---:|
| 1% | about 8 pairs | about 2 pairs |
| 2% | about 32 pairs | about 8 pairs |

Do not use the two-pair calculation as a launch protocol; retain the larger multi-launch design above. Distinguish detection from acceptance: if the minimum useful gain is 1%, a 95% ratio interval wholly below **0.99** is needed, not merely below 1. A true 1% effect cannot reliably clear a strict 1% lower-bound requirement. Report the interval, all pair ratios, range and sign changes; an interval wholly within a predeclared equivalence band can support equivalence, whereas an interval merely crossing 1 cannot.

For a claimed sub-2% gain, also qualify code-layout sensitivity. Isolated hot-function experiments can use ADR's same-process driver and reversed linking. For whole WRF, balanced relinking/order perturbations of both images provide an analogous robustness check, but do not claim they satisfy the literal same-buffer rule. Do not combine extra variants with repeated significance checking until one wins; predeclare comparisons and sample counts.

## Ranked next steps for PhiWeather

1. **Correct the record and freeze the candidate.** Record the early pair as unresolved, distinguish latest completed work from stale "to run" passages, and keep the corrected linked-object/path gate. Strengthen consumption evidence for the hot functions; qualify only merges whose original input gates passed. No new instrumentation scope is needed yet.
2. **Finish the numerical screen before a performance acceptance claim.** Resolve zero-field logic, genuinely held-out calibration, bias thresholds, low-power fields and early 3-D cadence; demonstrate fault rejection. Apply the frozen gate to the full and restricted candidate as needed. A screen pass is not forecast-skill acceptance.
3. **Measure once with a declared stopping rule.** Use balanced paired launches, estimate launch-level variance with the pilot, then spend the fixed confirmatory budget justified by the desired 1-2% sensitivity. Keep every valid result. Stop the PGO performance investigation if the useful effect cannot be resolved economically.
4. **Diagnose the existing full/restricted twins before adding objects.** Attribute dynamic time, hot-code growth, x87 spills, memory-helper traffic and hot/cold placement. Relink selected hot objects as diagnosis arms only after identifying an opportunity. Static call-site growth alone is insufficient.
5. **Test transfer independently of decomposition.** Evaluate P_O, P_H and the merge at one production layout on held-out weather/time regimes. If necessary, collect same-case/different-layout profiles; choose merge weights from intended deployment work. Cover quiet and later forecast periods before calling the merge generally representative.
6. **Treat LTO or GCC 16 as separate follow-up experiments.** First qualify the installed LTO tools and archive/OpenMP route, then compare LTO alone and LTO+PGO with fresh profiles. A GCC 16 port may improve the available optimization and training machinery, but needs its own WRF correctness, profile-consumption and timing evidence.
