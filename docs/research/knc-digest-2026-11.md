# What we now believe about KNC

S12-13, 2026-11-14. Owner summary; references resolve through
[the reference index](knc-references.md).

For M4, the best next work is still understanding the strict, serial paths
that actually take time: scalar floating point and its register transfers,
indexed loads and ordered sums, and instruction scheduling with one active
thread. The documents narrow these questions but do not establish a speedup.
One thread can issue only every other core cycle. Four active siblings can
cover a four-cycle arithmetic dependency; they cannot hide every longer
conversion, swizzle or memory dependency. We must price those paths separately
and keep call saves and memory transfers visible (R01 pp.19,23–24; R02 pp.32–34;
R03 pp.15–22).

Our old “all vectors use U, so two vectors never pair” rule is too broad.
Rahman's V-pipe list includes some stores and packstores, and pairing also
depends on instruction length, prefixes and operands. This warrants a small
production experiment on the instructions our candidates use, not an immediate
scheduler rewrite (R02 pp.34,56; R10 p.16). Gather cost likewise depends on
occupied lines, cache residence and the entire retry loop. Gather evidence
does not price scatter or make a strict sum reorderable (R05 pp.4–5).

Several proposed improvements already exist. GCC-KNC emits two-level software
prefetch with 16/32-line defaults and a footprint adjustment. It exposes
256 KiB to loop cache heuristics although physical L2 is 512 KiB. NGO stores
have been measured and implemented. Libgomp defaults to delay 128 and about
200 ms of spin, and derives an arena cap while respecting the user's setting.
Its optional grouped barrier was slower than the Linux barrier in the reported
local test. These are starting points to evaluate, not missing features to
implement again. No document supplies one best density, prefetch distance or
arena count for every program.

Huge pages are possible. Intel documented card-side THP in a named early MPSS
update, and our later bandwidth note reports actual explicit huge-page
allocations. Neither establishes the backing of today's ordinary malloc.
The 4 KiB hardware-prefetch boundary, translation reach and actual mapping
must be distinguished (R01 pp.19,22–23; R09 pp.4–5). **Superseded:** ~~R09's
performance table is explicitly pre-production and used an older stack than
its THP advice.~~ R09 p.4 reports libhugetlbfs results on MPSS 2.1.4346-16;
p.5 adds THP-stack results on 7110P (2.1.4982-15) and 7120P (2.1.6720-15).
All are pre-production on 2.6.x uOS. None establishes current MPSS 3.7 malloc
promotion or backing; S12-12 G08 is still needed.

Strict floating point remains a correctness gate. IMCI documents gradual
underflow and sticky exception flags but no vector FP traps; x87 has different
precision and trapping behavior. FP64 divide/sqrt expansions now exist in our
source, but source presence and instruction counts are not numerical proofs.
The Fortran runtime's underflow comment still conflicts with the architecture
description and needs input-subnormal and tiny-result cases separated.
Production errata also constrain mask context switching, fault-handler MXCSR,
uncacheable packstores and x87 exception clearing (R04 slides 9,18; R27
pp.39,55–56,660; R12 pp.22–25).

We now have the core PMU manual: two 40-bit counters per hardware thread.
We still lack proof of access on our image and a qualified uncore interface.
S12-12 prepares the PMU, prefetch/store, page, libc/libm, branch and allocator
diagnostics. S12-06/07/08 retain their own scalar/gather/pairing work. Until
the lead runs them, the recommendations below remain conditional. The useful
change today is more precise knowledge and review criteria; no compiler,
runtime, kernel, card-runner default or milestone rule changed in this ticket.

## Evidence and priority

**Verified** means directly read in the local document or named source
snapshot, including what a paper says it measured. It does not mean reproduced
on our card. **Reported** means an earlier project measurement or an unavailable
underlying source. **Inference** means a proposed consequence or investigation.
Rows separate these meanings instead of labelling an unmeasured recommendation
“verified.” All cheapest proofs below are future closure criteria, not tests
run by S12-13.

The compiler and runtime audit uses shared GCC revision
`619e14b479a952edff32e94f22573710d0b8ac17`. Paths starting `gcc/`, `libgomp/`,
`libgcc/` or `libgfortran/` are relative to `.work/_shared/gcc/`; `tools/` and
`docs/` are project paths. Installed binary and deployed kernel identity remain
separate questions. This is a read-only source audit.

Tables rank expected investigative value for **M4 first**, then
**PhiNix/later**. “Gate” precedes any affected optimization regardless of its
speed ranking. There is no numerical gain forecast or sum of overlapping hot
regions. The S12-12 column follows that ticket's actual scope: G06, G04, G08,
G05, G07 and G10. A “No” does not mean an experiment has passed.
