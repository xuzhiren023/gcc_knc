Owner, 2026-11-15: first M5 sprint (not Sprint 13). Lead test 2026-11-15 (CURRENT_STATE "Generic vector types"):
vector_size(64) compiles to IMCI, but vector_size(32) and (16) are lowered element by element to x87, and a 16-byte
vector passed by value is a hard error ("unsupported KNC register ABI mode"); 32-byte by value only warns (-Wpsabi).
FFTW's generic-simd128/256 codelets use exactly these types, so they get no IMCI today.

Before dispatch the lead writes an ADR (amending ADR-0014): how 16- and 32-byte generic vectors live in zmm (low
lanes, upper lanes undefined or zero, masks for loads/stores so no access past the object), and how they are passed
and returned by value under -march=knc (zmm registers or memory), x86 unchanged.

Deliver, per that ADR: V2DF/V4SF/V4DF/V8SF (and the integer modes FFTW needs) as legal KNC vector modes mapped to
masked IMCI operations on the low lanes; loads and stores that never touch bytes outside the object (masked or
unaligned-safe forms); by-value arguments and returns per the ADR; the hard error removed. Red-then-green T1: a
vector_size(16) and (32) kernel each emits zmm arithmetic and no x87 for the vector ops; a by-value call round trip;
a load/store at the end of a page (guard page) on the card. Accept: FFTW 3.3.x built with --enable-generic-simd128
and --enable-generic-simd256 passes its own `make check` on the card, and a paired FFTW bench (scalar build vs
generic-simd, and vs GCC 5.1.1 scalar) at full/3100/5100. T0-T2, ICE sweeps, x86 identity by the lead.
KCVI (FFTW's native KNC backend) stays separate: it needs the ADR-0013 intrinsics header.
