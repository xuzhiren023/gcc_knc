Today `tools/card_run` binds every job to all of physical cores 40-59, in `cpu_binding`, near line
179. It refuses whenever another project's `"timingValid": true` row is open (S5-04).

Deliver, each with a fake-transport test in `tests/tools/test_card_run.py`, red first:

1. **A thread count per job.** A new option, `--threads N` (default 1), or a config key. The job
   takes ceil(N/4) physical cores and all 4 logical CPUs of each, so one core fills before the
   next. `--cores LIST` keeps an explicit layout for jobs that need one.
2. **Cores come from the ledger, not a fixed range.**
   - Free cores are physical cores 0-59 that no open ledger row lists in `"cores"`, from any
     project. Core 60 is never used.
   - Take free cores from 59 downward; the other project takes them from 0 upward.
   - If too few are free, wait within the admission timeout, then refuse with no row written.
   - The start row records the exact cores and logical CPUs, and `claude-pin` pins to them.
3. **Benchmark and atomic jobs: `--benchmark`.**
   - The job needs an empty ledger (no open row at all), takes all cores 0-59, and writes
     `"timingValid": true`.
   - Round robin: if the last finished `timingValid` row was ours, and another project has an
     open `"queued"` row with `"timingValid": true`, refuse with "their turn".
   - When ours has to wait, `card_run` writes its own `"queued"` row and removes it when it starts
     or gives up.
   - A `"queued"` row stays open until a row with the same `jobId` and event `start`, `finish` or
     `superseded` follows it. The PhiWeather session writes them in the form
     `{"agent":"claude","project":"PhiWeather","event":"queued","jobId":"claude-mentor-…","timingValid":true,"cores":[0..59]}`.
   - Only queued rows with `"timingValid": true` and a `queuedTime` younger than 3 hours count.
     The ledger holds 29 legacy `gpt61` queued rows with neither field; ignore them. A finish row
     with outcome `"cancelled"` also closes a queued row. Our own queued rows carry the same
     fields.
   - **No starvation:** while another project has an open `timingValid` queued row, our
     non-benchmark jobs do not start either. They wait within the admission timeout, then refuse,
     so the ledger can drain for the other project's turn.
4. **Unchanged:**
   - non-benchmark jobs never start while any `timingValid` row of another project is open (S5-04);
   - the memory budget;
   - the staging limit;
   - the project tag.
5. `harness/card/run_suite.py` is lead-owned; do not edit it. Expose `--threads` so the lead can
   pass the suite's `-j` count.
6. Update `docs/card-run.md` in a few lines.
