S3-11's trunk build (`docs/research/m1-result.md`, Y1) stopped in `gentarget-def`: **duplicate
definition of `atomic_storeti`**. Upstream commit `d9e21f7c4d1` ("x86-64: Add -m128bit-atomic",
July 2026, after 16.2) added `atomic_loadti` and `atomic_storeti` to `sync.md` under
`TARGET_128BIT_ATOMIC_ENABLED` (`TARGET_CX16 && TARGET_SSE2 && TARGET_128BIT_ATOMIC`). Ours is in
`imci.md` under `TARGET_KNC` and calls `__atomic_store_16`. An optab name cannot be defined twice,
so the next rebase onto a release with that commit breaks the build. KNC has neither CX16 nor
SSE2, so upstream's condition is false for KNC: the clash is a name clash, not a design clash.

Make the KNC side rebase in one line:

1. In `knc`: move the body of KNC's `atomic_storeti` (and, for the same reason, `atomic_exchangeti`)
   into helpers in `i386-knc.cc`, so each `imci.md` expander is a `TARGET_KNC` condition and one
   call. No change in behaviour.
2. Write the trunk resolution in `docs/research/forward-port.md` as a recipe: drop KNC's
   `atomic_storeti` from `imci.md`, and in upstream's `sync.md` expander add `|| TARGET_KNC` to the
   condition and an entry hook, `if (TARGET_KNC) { ix86_knc_expand_atomic_store (operands); DONE; }`
   (ADR-0006 rules 1 and 2). Check upstream's `atomic_loadti` too: if it can never be enabled
   with `-march=knc`, even with `-m128bit-atomic`, say so with the reason; if it can, that is a
   finding for this note.
3. Apply the recipe to S3-11's trunk tree (`.work/_shared/portability/trunk`, with its four
   recorded resolutions), build C-only `cc1` for `k1om-mpss-linux`, and run T1 and T2 against it,
   compared with 16.2 at this ticket's head. Every difference gets a cause. Builds run only while
   no other build runs.
