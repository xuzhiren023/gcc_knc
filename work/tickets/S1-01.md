From S1-02 on, most work changes the GCC fork in `.work/_shared/gcc`, a separate repository
with one checkout (ADR-0001). Today `pm.py` only branches, checks and merges this repository,
so GCC commits would bypass review and red-then-green would not be visible. The fork's
integration branch is `knc`, at tag `releases/gcc-16.2.0`. Nothing here pushes.

A ticket opts in with `gcc: yes` in its front matter. WIP is 1, so one shared checkout is
enough; the ticket's GCC branch has the same name as its branch here (`s1/S1-02`).

Acceptance (T0, in temporary repositories like the existing harness tests):

- [ ] `pm.py start` on a `gcc: yes` ticket creates its GCC branch from `knc`, or reuses it, and
  checks it out in `.work/_shared/gcc`. It refuses if that checkout has uncommitted changes, or
  has another ticket's branch checked out
- [ ] `pm.py submit` refuses uncommitted changes in the GCC checkout, records `gcc_head`, and
  counts the GCC diff (`knc...branch`) in the changed-line budget together with this repository's
- [ ] `pm.py approve` merges the GCC branch into `knc` with `--no-ff` after the machine check, and
  refuses if the GCC branch moved since submit. If either merge fails, neither is left half done
- [ ] The script review can see the GCC change: `LEAD_PROMPT` names
  `git -C .work/_shared/gcc diff knc...<branch>` and `log`, and the lead's allowed tools include
  read-only `git -C .work/_shared/gcc log`, `diff` and `show`
- [ ] Tickets without `gcc: yes` behave exactly as now; the existing harness tests still pass
- [ ] `docs/COLLABORATION.md` gets two lines on how a GCC ticket works

Out of scope: pushing, and the hook rules. Engineers still never run `git merge` or `git push`.
