- 2026-11-12 17:19 lead changes: Profiles, sealing, serial-vs-serial voting, the HPCG staged fix, the SQLite fallback and the runtime-prefix record are right, and the tests are proportionate. Two things must change before the card run. (1) tools/corpus/polybench_capture.c:20 with tools/corpus/launch.c:109: the full-array dump now runs %.17g printf for every element (262k values for gemm, jacobi-2d and heat-3d) through stdout and ssh, and this happens inside the CORPUS_TIME window, which covers the whole child. On a 1 GHz in-order KNC core that formatting costs about as much as the kernel, so it pushes every PolyBench speedup toward 1.0 and makes the vote meaningless. Keep the output complete but take it out of the timed region. For example, the capture can fwrite raw doubles with the array names to a file, and launch.c can print them as CORPUS_ARRAY lines after CORPUS_TIME (hex %a or %.17g, either is fine). The same applies, less severely, to roundtrip.c writing packed.bin inside the timed run: move the write after the timing, or say in the README why it is negligible. (2) tools/corpus/roundtrip.c:50: the corrupted-result control flips a byte of output and checks that memcmp sees it. That is always true and does not test any check. Make the control go through the real cross-compiler path: give the peer decoder a copy of packed.bin with one byte flipped, and print CORPUS_CONTROL rejected only when that decode fails or its output differs from input.bin. The host requirement in output_result can stay as it is. Note for the native run, not a change: serial NPB-EP/CG/MG class A with one thread on a KNC core may exceed the 120 s timeout. List that risk in the submit note so the lead can calibrate on the first pass.
