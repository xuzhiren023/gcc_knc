Owner (2026-11-10): card turns are now round robin with the other project, so our jobs no longer
need the shared memory limit, "but we do need to make sure our optimization works under different
spec size". GCC-KNC must suit the 3100 (57 cores, 6 GB), 5100 (60 cores, 8 GB) and 7100 (61
cores, 16 GB) families (ADR-0012, S9-13), and we have one 7120P.

Deliver, in `tools/card_run`:
- `--profile 3100|5100|7100|full`: a job that runs as that card would. It sets the compute cores
  (the card's cores without its OS core: 56, 59, 60; on our card cores 0-55, 0-58, 0-59) and the
  address-space limit (`RLIMIT_AS`) to the card's usable memory (3100: 5.5 GiB, 5100: 7.5 GiB,
  7100 and full: the 7120P's free memory less the 1.5 GiB margin). State the values as named
  constants with their source.
- Allow `--benchmark` with an explicit core set when it comes from `--profile`: the job still has
  the whole card to itself (no other job of ours or theirs), it just uses fewer cores.
- In our exclusive turns, the memory budget is the card's free memory less the margin, not the
  shared-mode 10 GiB (`MEMORY_BUDGET_MIB`); keep the 10 GiB cap only when another project's job is
  running.
- In our exclusive turns there is no core limit either (owner 2026-11-10): non-benchmark jobs may use
  any of cores 0-59, and the shared-mode 40-59 rule applies only while another project's job runs.
- The receipt and the ledger row record the profile.

What a profile cannot stand in for, and the help text must say so: the clock (1.1, 1.053, 1.238
GHz) and the memory bandwidth per core (about 4.2, 5.3, 5.8 GB/s). Fewer active cores raise the
bandwidth each core gets, so a profile is a fair test of correctness, memory size and core
count, and only a rough test of memory-bound speed.
