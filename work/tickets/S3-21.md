**Wrong code, found on the card by the lead on 2026-11-03.** `gcc.c-torture/execute/pr65369.c` at
`-O2 -march=knc` segfaults on the card. Built with `-fno-tree-vectorize`, at `-O0`, or by the
donor, it passes. Of the full execute suite (1,661 programs), it is the only real failure.

`bar` copies sixteen 4-byte pieces with `memcpy` from `block = input + 1` (byte-aligned). Basic-block
SLP vectorizes them with 64-byte vectors into:

```
vloadunpackld  (%rdi), %zmm0
vloadunpackhd  64(%rdi), %zmm0
```

Intel 327364-001, `VLOADUNPACKLD` (p.361): the stream starts "at the element-aligned address mt",
and the pair allows "vector loads that are only element-wise, not vector-wise, aligned". So the
pairs need at least element alignment: 4 bytes for V16SF/V16SI, 8 for V8DF/V8DI. The same holds
for `vpackstore*`. ADR-0005 point 4 and S3-05 allowed `movmisalign` for any alignment. S3-03's
probe only tested whole-element offsets, so it could not see this.

Fix (ADR-0006: logic in `i386-knc.cc`, hooks only in shared files):

1. **Vectorizer:** KNC's `support_vector_misalignment` answers yes only when the access is known to
   be element-aligned. That means: not packed, and the type's or the reference's alignment is at
   least the element size, with a misalignment that is a multiple of it (or unknown, given that
   alignment). Otherwise no. Check the SLP and loop paths both consult it here.
2. **Explicit accesses:** `ix86_knc_expand_packed_move` must not emit a pair when `MEM_ALIGN` is
   below the element size, for example a packed struct member or an `aligned (1)` vector typedef.
   Use a legal byte-granular path instead, such as a copy through general registers into a
   64-byte-aligned stack slot, and say which in the submit note.
3. Amend ADR-0005 point 4 in the same change; the lead reviews the wording.
