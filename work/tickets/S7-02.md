Facts already settled (do not re-derive):
- `docs/research/donor-inventory.md` lines about `libgfortran/configure.host`, `config/fpu-387.h`
  (lines 30-42, 94-104, 174-194) and kind 16: `has_sse` gates all MXCSR access, and CPUID reports no
  SSE on KNC, so libgfortran skips MXCSR entirely.
- Lead card probe (2026-11-03): on KNC, MXCSR bits 7-12 (the x86 exception masks) are reserved and
  writing them faults; bit 21 must be kept (backlog E6-02).
- The card's GCC 5 `libgfortran` uses pre-GCC 8 array descriptors; never mix it with GCC 16's.

Questions:
1. **FP control on KNC:** which libgfortran entry points read or write the FP environment (IEEE
   modules, `fpu-387.h` routines, rounding modes, exception flags and halting), what each must do with
   x87 and with KNC's MXCSR (which bits exist, which fault), and the smallest safe design.
2. **Descriptors and ABI:** GCC 16's descriptor layout versus GCC 5's, and what that means for mixing
   objects or `.mod` files; how to keep GCC 16 programs from picking up the card's old
   `libgfortran.so` (soname, rpath, static linking).
3. **`real(16)` / libquadmath:** on k1om, `long double` is x87 80-bit in 16 bytes (S1). Is kind 16
   the 80-bit type or `__float128`? Does libquadmath build without SSE? Recommend a decision.
4. **The slice:** which libgfortran parts the backlog's slice needs (descriptors, allocation,
   formatted I/O, modules) and which configure or source spots block a k1om build, found statically.
