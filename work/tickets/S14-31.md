Twin lead 2026-11-16, from knc-boinc's first 8-core use of 0.4.0 (their S1-06; evidence
`C:/Users/xuzhi/Documents/knc-boinc/.work/S1-06/docs/twin-multicore.md` and `twin/multicore/`, read-only). Four gaps
that stop a user from asking "does my kernel keep its per-core speed from one to eight cores":

1. `compare` refuses core vs unit/ring results because unit/ring load `profiles/multicore-assumed.json` and the profile
   hash differs even with the same `--profile`. Give `compare` (and `batch`) a documented cross-scale mode: equal
   `unit_of_work` per context, the same core profile hash (record the core profile hash separately from the multicore
   overlay hash in result.json), and a result that reports per-context cycles per unit at each scale and their ratio,
   labelled `unvalidated_scenario_estimate` while S14-21 is open.
2. Unit/ring reject stubs (`calls`), so an OpenMP caller (GOMP_loop_*) cannot be kept; and there is no input form for
   repeated calls of one function with new arguments per call (one gravity call is one body; the user's unit is a
   128-body chunk). Add `entry: function` with a `calls_table` (per-call register arguments and count, per context) so
   a stream is N calls of the function, and accept costed stubs at unit/ring scale with the same rules as core scale.
   The same form serves S14-21's GEMV binding.
3. `sample-loop` needs exactly one context and unit/ring bypass the sampler. Allow sampling with several contexts when
   every context samples the same loop label (stop when every context's windows agree; report per-context series), at
   core scale first; at unit/ring scale, refuse with a message that names this ticket until it is modeled.
4. result.json at unit/ring scale has no separated stall shares for ring hops, directory lookups, controller queue
   waits and core-local misses (the queue waits overlap). Attribute stall cycles by first blocking cause, as the core
   engine does, and print the shares in summary.md.
