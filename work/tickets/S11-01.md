Owner's user story (2026-11-11): "Research the best way of moving data back and forth between host and
knc. How do we apply it in our projects. Ssh and scp are slow, I used to do dma, which works on phichat
but failed repeatly in phiweather. So I want a fresh start and make a best practice."

As the owner: I know which transfer method to use for each kind of data (commands, small files, test
suites, multi-GB binaries and datasets, results back to the host), how fast and how reliable each is on
our Windows host and 7120P, and our harness and projects use it.

Today: `tools/card_run` stages files as SSH stdin streams to guarded `cat` and reads results back in
64 KiB stdout chunks (`docs/card-run.md`); uploads have hit SSH deadlines under host load (S10-05 card
turn, 2026-11-11: 4 jobs, `upload-claude-pin: SSH upload deadline`). Prior art, read-only and not a
requirement (CLAUDE.md):
- PhiChat uses MPSS SCIF DMA for bulk uploads with SSH/SCP fallback and states it works on this
  7120P (`C:\Users\xuzhi\Documents\PhiChat\docs\SCIF-TRANSFER.md`: Windows MPSS driver plus the card's
  `libscif.so.0`, two registered 64 MiB buffers, file-backed receive windows, nonce-bound connection).
- PhiWeather held DMA after a Windows 0x7E crash during a DMA transfer, faulting driver unknown
  (`C:\Users\xuzhi\Documents\PhiWeather\PLAN.md`, around lines 1400-1450).
Read both for facts only; write our own code (no copying from either tree).

Deliver:
1. **Inventory** (`docs/research/host-card-transfer.md`), facts with sources, for each method that can
   work with the installed MPSS on Windows and the card's MPSS 3.7.1, with no driver install and no MPSS,
   module or `/etc` change:
   - SSH/SCP: cipher and MAC choice (what the card's sshd offers), compression, one connection reused
     (ControlMaster or a persistent session), parallel streams, tar pipes;
   - raw TCP over the `mic0` virtual Ethernet (netcat or a small socket program; MTU);
   - SCIF messaging (`scif_send`/`scif_recv`) and SCIF RMA/DMA (registered windows, `scif_writeto`,
     `scif_vwriteto`, `scif_readfrom`, `scif_mmap`), from the host and from the card side;
   - anything MPSS provides above SCIF that applies here (COI buffers, `micnativeloadex`, NFS or
     virtio from the host) and whether it exists on a Windows host.
   For each: direction support, limits (pinned memory, window sizes, page alignment), failure modes,
   cleanup on disconnect, and licensing of headers and libraries (ADR-0013: link the installed MPSS
   libraries, do not redistribute Intel files).
2. **Why DMA failed in PhiWeather and not in PhiChat**: compare what each did (buffer sizes and
   lifetime, registration pattern, concurrency, card load during transfer, error handling, process exit
   with windows registered) and list the hypotheses for the 0x7E crash with what would confirm each.
   Design our DMA path so that each hypothesis is avoided, and say how.
3. **Measurement tool**, staged for the lead (no card job by the engineer, ADR-0010 pairing):
   host and card programs (card side built with the GCC-KNC prefix) that move 4 KiB, 1 MiB, 64 MiB and
   1 GiB both ways by each viable method; report throughput, latency per small transfer, host and card
   CPU time, and a SHA-256 per transfer; repeat each 20 times; run once with the card idle and once with
   240 busy threads. The DMA trials ramp up (small sizes first, one transfer at a time, then
   concurrency), every run checks the host's event log for a new bugcheck before the next step, and
   the runner stops on the first integrity error. The lead runs it only in our exclusive card turn.
4. **Recommendation and plan** (in the research doc, plus a draft ADR in the submit note for the lead):
   the method per data kind with its measured speed; a fallback order; and how to apply it to
   `tools/card_run` and `harness/card/run_suite.py` (S11-02 implements), to PhiNix later, and the advice
   to send PhiWeather and PhiChat (the lead relays; their folders stay read-only).

- 2026-11-12 07:31 lead answer: Yes. The AGENTS.md rule is about process provenance (receipts, hash manifests of our own files), which git already covers. The SHA-256 in deliverable 3 is part of what the tool measures: it checks that the bytes sent are the bytes received. So compute SHA-256 inside the host and card programs over each transfer's payload, compare the sender's and receiver's digests in memory, and print the digest and match/mismatch in the benchmark result lines. The runner stops on the first mismatch. Do not write hash files, manifests or receipts. Write one small portable C SHA-256 of your own from FIPS 180-4 and build it for both host and k1om (no OpenSSL dependency on the card). Check it once against the FIPS 180-4 'abc' vector inside the existing loopback/fake-transport test, not as a separate test file. Keep the time spent hashing out of the throughput figures: hash outside the timed region, or report it on its own.
