GCC 16 for `k1om-mpss-linux` emits emulated TLS: `__thread int tv; return tv;` compiles to `call
__emutls_get_address`, at `-O2` and with `-fPIC`. The donor emits native TLS (`movl %fs:tv@tpoff,
%eax`, and `te@gottpoff(%rip)` for an extern). So a `__thread` variable defined by donor-built code
or a system library and used from a GCC 16 object, or the reverse, refers to two different things.
That breaks mixed native code, which is what M1 is about (found by the lead on 2026-11-03).

Cause: `gcc/configure.ac`'s TLS assembler test matches `i?86-*-* | x86_64-*-*` only (the
`tls_as_opt` / `conftest_s` block near line 3995), so for `k1om-*-linux*` it never runs, and
`HAVE_AS_TLS` stays undefined in `gcc-build/gcc/auto-host.h`. S1-02 added `k1om-*-linux*` to
`config.gcc` and to one `configure.ac` case (line 4810), but not to this one.

Also audit the rest. `gcc/configure.ac`, `libgcc/configure.ac`, `libgcc/config.host`,
`libgfortran/configure.ac` and `config/*.m4` have about 73 `x86_64-*-*` patterns without
`k1om`. For each one, record in `docs/research/k1om-configure-cases.md` whether k1om should take
the x86_64 branch, with the reason and the configure result before and after. Change only the
ones that should. Regenerate each changed `configure` with GNU autoconf 2.69, which is at
`.work/_shared/toolchain/autotools/bin` (with m4 1.4.19). Put that directory, then the Cygwin
toolchain's `bin`, first on PATH, under Cygwin `sh`. The lead checked that it regenerates GCC
16.2's `gcc/configure` byte for byte. Never hand-edit a generated file. The commit carries
`configure.ac` and `configure` together, and the diff of `configure` should contain only what the
`configure.ac` change implies.
