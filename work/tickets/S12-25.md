PhiWeather, 2026-11-14 (reply to the lead's threads-per-core note): their production WRF runs 8 MPI ranks x 15
OpenMP threads = 2 threads per core on the 60 compute cores (OS core excluded; threads 0-1 of each core; OMP_PLACES=
threads, close, ACTIVE; numtiles 5x3 = one tile per thread); 3 threads/core measured 22% slower. GCC-KNC schedules
for 4 active threads per core by default (`--param=knc-threads-per-core=4`, also under -mphinix), and one thread
cannot issue in back-to-back cycles (R01 pp.19, 23-24), so a build scheduled for 2 may suit their runs better.

After S11-26 stages the default build: build a second smpar tree identical to S11-26's except
`--param=knc-threads-per-core=2` added to FCOPTIM and CFLAGS_LOCAL (same prefix, same WRF tree, no workarounds),
stage it as `smpar-tpc2/` with RUN-NOTES.md (exact flags, prefix commit, build log, check-wrf-links.py result), and
record in the notes how much generated code differs (objdump instruction count per hot physics object, at least
the S11-23/S11-25 files). PhiWeather times both builds at 8x15 on the same case with their own card time; the lead
relays their result here. Host build only; message the lead before starting (PhiWeather pauses host builds).

Parked by the owner, 2026-11-14: no WRF rebuild just for flag arms; GCC-KNC should take latency and threads-per-core into account itself (S12-21, S12-27). Reopen only if the owner asks.
