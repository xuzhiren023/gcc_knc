Lead 2026-11-16 (Codex, never Fable). Finding from S14-14's regress run and the lead's reproduction: 
`tests/regress/test_knc_twin.py::test_heldout_predictions_unchanged` fails on `s12-31-hpcg-104` under Cygwin
Python 3.12 although the engine and profile are unchanged. Cause: `knc-twin/tests/trial/knc_trial.py`
`predict_heldout` calls `validate_heldout.predict_case` with its default `max_seconds=120.0`; the 8000-row case
needs longer than that on a slow interpreter or a loaded host, every variant comes back as
`{"status": "budget_exhausted", "message": "python time budget exhausted after N simulated cycles ..."}`, and the
test compares that stub with the full recorded prediction (a 10 KB diff with no hint of the cause). The recorded
`prediction.json` was made with a long budget. The test is therefore host-speed dependent, not a determinism check.

Fix (main's `knc-twin/`):
- `predict_heldout` (and `validate_heldout.compiled_rows` when `record=False`) must run a held-out replay without a
  wall-clock budget, or with one of at least one hour; `predict_case` takes `max_seconds=None` meaning no deadline.
- The regress test asserts first that every variant's `status` is `ok` and fails with the variant's `message` when
  it is not (one line, not the dict diff); only then compares with the recording.
- `validate_heldout.py --record` refuses to write a `prediction.json` that contains a non-`ok` variant.
- Red first (an `s12-31-hpcg-104` replay with a 1-second budget must produce the one-line failure), then green; add
  no test file (extend `tests/regress/test_knc_twin.py` and `knc-twin/tests/test_v03.py`). Then `knc_twin.py
  selftest` and the full regress single-threaded, and report the replay's wall time under the interpreter used.
