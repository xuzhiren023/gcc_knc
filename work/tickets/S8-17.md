Owner's question (2026-11-08): why does the card stay at 160-180 W after vectorization, when the
vector unit should draw more? S6-13 measured whole-card power on the memory-bound M2 affine kernel
(x87 171.7 W, GCC-KNC 166.9 W, IMCI 163.8 W), never a saturated vector unit and never the per-rail
split. C12 measures both.

Add check C12 to the knc-char corpus (`tests/bench/knc-char/`, one source file plus its job lines),
using the m2 fixture's power reader (`tests/acceptance/m2_kernels/power.c`) or a copy of its parser.
One `--benchmark` job at 60 cores x 4 threads runs these phases, each for a fixed time (default 20 s,
`--phase-seconds`), in the interleaved order idle, x87, fma, stream, fma, x87, idle:
- **idle:** the workers sleep on a barrier;
- **x87:** register-resident scalar `fmul`/`fadd` chains, no memory traffic in the loop;
- **fma:** register-resident `vfmadd231ps` on enough independent zmm accumulators to hide the
  4-cycle latency at 4 threads per core (at least 2 per thread), no memory traffic in the loop. This is
  the vector unit at its peak issue rate;
- **stream:** a memory-sized read-modify-write vector stream (S8-01's C1 sizing), to load the memory rail.

A sampler thread (unpinned, as S6-13 round 2) reads `/sys/class/micras/power` every 50 ms. It
records line 1 (whole card) and lines 8-10 (core, uncore and memory rails, watts and volts), and once
per phase `scaling_cur_freq` and the die temperature, if `/sys/class/micras/temp` exists. Print one
line per phase with:
- mean, min and max watts for the whole card and each rail;
- the work done (GFLOP/s for x87 and fma, GB/s for stream);
- energy per operation.

Drop the first second of each phase, so the sensor's averaging window has settled.
