Found by S5-02 (`docs/research/knc-conversions.md`, section 5). `tools/knc_lint` assembles the `.s`
and also decodes the object or binary. The K1OM `objdump` prints the register source of
`vcvtdq2pd`, `vcvtudq2pd` and `vcvtps2pd` as `%ymmN`: these forms read only the low 8 lanes. The
encoding (for example `62 f1 7a 08 e6 c1`) is the same whether the source is written `%zmm1` or
`%ymm1`. The lint's register rule (`tools/knc_lint`, near lines 24 and 37) denies every `%ymm`, so
it rejects correct KNC code. S5-02's probe hits this, and so will the conversion tickets as soon
as GCC emits these instructions.

Deliver:
- In the decoded-binary check only: accept `%ymmN` as the register source operand of exactly
  these three mnemonics (any masking and swizzle suffixes). Keep every other `%ymm` a violation,
  including in the assembler-text check and as a destination.
- Tests in `tests/tools/test_knc_lint.py`, red first:
  - each of the three decoded forms passes;
  - `%ymm` as their destination is still rejected;
  - `%ymm` in any other mnemonic is still rejected;
  - a `%ymm` written in the `.s` text is still rejected.

Acceptance:

- [ ] Red first, then green: `python -m unittest tests.tools.test_knc_lint`
- [ ] `tests/regress/knc-convert-probe.c`, built with the command in its header, passes
  `tools/knc_lint` on its `.s` and its binary
