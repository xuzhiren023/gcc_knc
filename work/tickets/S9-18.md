Owner (2026-11-10): "write a small test about profile-guided optimization, and about the compiler
seeing which branch is most likely ... and see how effective it is." Backlog E7-08 (PGO on the card)
and E7-04 (branch cost from C10) are M4 items; this is an early measurement, no compiler change.

KNC is an in-order core with no CMOV (S1-04), so taken branches and block layout cost more than on a
big x86 core; C10 measured the branch-mispredict penalty but no default uses it yet.

Deliver, under `tests/bench/pgo/` with a build script (`tools/s9_18_pgo.py`):
1. Four small single-thread kernels, each self-checking and printing a checksum:
   - **skewed**: a hot loop whose data-dependent branch goes one way 95% of the time, with a heavier
     rare path;
   - **dispatch**: a small bytecode interpreter (switch over about 20 opcodes, skewed opcode mix);
   - **calls**: a hash-table insert and lookup or a sort with a comparator, where inlining and
     hot/cold splitting decide speed;
   - **pointer**: a linked-structure walk with a rarely taken error path.
2. Builds of each with the GCC-KNC prefix: `-O2 -march=knc` (baseline, GCC's own static guesses);
   `-O2` with correct `__builtin_expect` hints; `-O2` with wrong hints (the cost of a bad guess);
   and PGO in two steps: `-fprofile-generate` (instrumented), then `-fprofile-use` from that profile.
   Also `-fprofile-use` with a profile from a different input mix, to show a mismatched training run.
3. PGO plumbing on the card, since the engineer cannot run the card:
   - Check the prefix has `libgcov` for k1om; if not, stop and ask.
   - Stage the instrumented binaries with a card script that runs them and prints each `.gcda` as
     hex to stdout (the card's BusyBox has `od`), and a host command
     `python tools/s9_18_pgo.py use <card stdout file>` that rebuilds the `.gcda` files and the
     `-fprofile-use` binaries and stages the timing set.
4. A timing runner: each variant against the baseline in one program per kernel, paired and
   interleaved as ADR-0010 asks, at one thread, several rounds, with a checksum check per run.

Acceptance:

- [ ] The kernels' checksums agree across all variants on the host (x86 build of the same sources)

- [ ] Report the code-size and assembly differences that explain each expected effect (block order,
  inlined calls, hot/cold split), so the lead's card numbers can be read against them
