sub-agent to do a deep research on this topic and make sure our coverage was good." Sprint 12 runs one improvement
round of three to at most five themes (`docs/sprints/SPRINT-12.md`, `docs/M4-DEFINITION.md`); this study decides how we
judge breadth when choosing them.

Act as a senior compiler engineer who has tuned compilers for real user code, not only benchmarks. Find ways to reach
broad benefit; back each claim with a cited primary source (papers, GCC and LLVM documentation and mailing-list or
bug-tracker evidence, vendor optimization guides with page numbers, ADR-0013 for Intel material) or with this
repository's measurements.

Answer:
1. **The code-style spectrum.** What do programs look like across skill levels and domains: tuned professional HPC and
   library code; ordinary scientific code by domain experts (Fortran and C, often written once and never tuned);
   student and amateur code (naive nested loops, wrong loop order, pointer arithmetic without `restrict`, arrays of
   structs, small functions called in loops, globals, `double` and `long` everywhere, little `const`, recursion,
   heavy branching, I/O-bound parts); generated code; C++ with abstractions (iterators, templates, `std::vector`).
   Use published studies of real-world code (for example corpus studies of loop shapes, aliasing, call density and
   vectorizability) where they exist; say where evidence is thin.
2. **Which compiler mechanisms help which styles on an in-order, 4-thread, x87-scalar, 512-bit-vector core with
   GDDR5** (`docs/research/knc-microarch.md`, `knc-characterization.md`, `knc-costs.md`): for example alias analysis and
   runtime alias checks, loop interchange and blocking for wrong-order loops, scalar replacement, inlining and call
   overhead, if-conversion and branch layout, address-mode and induction-variable quality, register pressure and
   spills, x87 versus vector-scalar FP, vectorization of reductions and of AoS data, prefetch, code size. For each:
   how much of each style's time it can plausibly remove, and its cost and risk in GCC 16 under ADR-0006.
3. **Coverage check of our corpus** (`docs/research/corpus-and-coverage.md`, the 17 programs, `tools/corpus/`): which
   styles it represents and which it misses (it is heavy on PolyBench and light on naive and C++ code). The M4 corpus is
   frozen (ADR-0015: no programs added after results); recommend a separate, unscored **generality check set** of small
   public programs or kernels written in the missing styles, used only to confirm that a Sprint 12 theme helps those
   styles too and never in the M4 score. Licences must allow use; list exact sources and versions.
4. **A theme-selection rubric** for Sprint 12: how to score a candidate theme by breadth (styles helped, development
   programs helped, generality-set evidence) as well as removable time, cost and risk, so that a theme that helps many
   styles beats one that helps one program a lot.
