From the scope review (finding 7) and backlog E7-21. S10-12 found that MPSS libm `cbrtl` faults (`s_cbrtl.S:178`
zero-extends a negative table offset; first fault `cbrtl(1e-5)`), and S10-13 redirected it. Whether other long
double entry points have the same pattern is a hypothesis, not a finding. Check it before the M4 correctness oracles
freeze, bounded to a reproducer-driven answer; this is not a libm rewrite.

Deliver:
- From the card sysroot's `libm` (`.work/_shared/toolchain/sysroot`), list the long double entry points and, by
  reading their disassembly (`k1om-mpss-linux-objdump`), those with table-indexed loads whose index can go negative
  in a 32-bit register before a 64-bit address (the `cbrtl` pattern); facts only, with addresses.
- A native multithreaded probe for the lead (every CPU it is given, AGENTS.md) that calls each candidate over every
  exponent residue and sign across the long double range, with a SIGSEGV handler reporting the function and input
  and continuing with the next function in a child process, so one fault does not hide others. Staged with the exact
  `card_run` command; no card job by the engineer.
- A short note `docs/research/mpss-libm-long-double.md`: candidates, probe design, and (after the lead's run) which
  functions fault. Each faulting function becomes a guard ticket like S10-13.
