Sprint 7 prework (owner, 2026-11-06), backlog E6-01. Read only: do not build GCC and run nothing on
the card. Write `docs/research/knc-libgcc-shared.md`. Answer each question with file:line in
`.work/_shared/gcc` (branch `knc`), a symbol table, or the card sysroot in
`.work/_shared/toolchain/sysroot`; mark each answer proven, inferred or unknown.

Facts already settled (do not re-derive): GCC-KNC builds a static libgcc today (S2-05, S3-14 with
native TLS); the donor is GCC 5.1.1 with its own `libgcc_s.so.1` in the sysroot
(`docs/research/donor-inventory.md`).

Questions:
1. **The donor's `libgcc_s.so.1`:** its exported symbols and version nodes (`GCC_3.0` ... `GCC_x`),
   and what the card's programs and libraries (sysroot `lib64`, `usr/lib64`) import from it.
2. **GCC 16's `libgcc_s`:** which version nodes and symbols it would add (libgcc's map files and
   `libgcc-std.ver`), and which of those need features the card lacks: glibc newer than 2.21
   (`GLIBC_2.x` imports of libgcc_s itself), kernel newer than 2.6.38 (system calls), SSE/AVX
   helpers, `__cpu_indicator_init` and CPU model detection, CET/shadow stack, `__float128`/`_Float128`
   and `TFmode` helpers.
3. **Compatibility:** can GCC 16's `libgcc_s.so.1` replace the donor's for existing card programs
   (a superset of its symbols, same versions), or must both coexist (different soname or path)?
4. **The unwinder:** `.eh_frame`, `PT_GNU_EH_FRAME` and `dl_iterate_phdr` on the card's glibc 2.21;
   anything in GCC 16's unwinder that needs newer glibc (for example `_dl_find_object`, glibc 2.35).
5. **Configure:** what `--enable-shared` for `k1om-mpss-linux` changes in libgcc's build
   (`libgcc/config.host`, `t-` fragments), and every KNC-specific blocker you can find statically.

Deliverable: the note, ending with a recommended plan for the E6-01 implementation tickets (2-4 of
them, each with acceptance) and the risks.
