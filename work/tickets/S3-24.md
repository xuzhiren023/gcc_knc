The owner asked on 2026-11-04 for fewer laptop builds, since `make` holds the CPU near 80% and the
laptop throttles. Two builds are repeated for nothing today:

1. **The shared tree's baseline build.** S3-23 started with a full `make` of
   `.work/_shared/gcc-build` (`S3_23_baseline_build-20261104-081207.log`, about 12 minutes,
   `cc1` relinked and selftests rerun) although that tree was last built from S3-22's tip, whose
   tree equals the merged `knc` head. Add `tools/gcc_build.py`: it runs the shared tree's `make`
   (same targets and flags engineers use now; read recent `.work/_state/logs/S3_2*_build-*.log`),
   and on success writes a stamp in the build directory with the source `HEAD` commit, its tree
   hash, and whether the worktree was clean. `--if-stale` exits 0 without running `make` when the
   stamp's tree hash equals the current `HEAD^{tree}` and the worktree is clean, and prints which.
   A dirty worktree or a missing or unreadable stamp always builds. A failed build removes the stamp.
2. **The x86 check's stock tree.** `tools/portability.py` `build_cc1` reruns `configure` and
   `make -j4 all-gcc` in both slots on every run (`tools/portability.py:144-149`), including slot
   `a`, which is the unchanging stock release. Write the same kind of stamp per slot (commit, the
   configure arguments, the make arguments). When the stamp matches and `gcc/cc1.exe` exists, skip
   both `configure` and `make` for that slot and say so. Reconfigure only when the configure
   arguments changed.

Use tree hashes, not file times: Git checkouts and merges change times without changing content.
