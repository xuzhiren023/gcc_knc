Owner's request (2026-11-12): "Find out how to break through KNC's 170-180 GB/s estimated real use case
bandwidth ceiling, and what measurement can we take to make the real use case bandwidth ceiling close to within
75%-85% of peak memory bandwidth."

**Your job is to find ways up, not to explain why it cannot be done.** The 170-180 GB/s figure is what tuned
STREAM-style codes usually report on KNC. It is a starting point, not a law. Treat every claim that a limit is
fixed as a hypothesis to test. Do not open the deliverable with the folklore ceiling, and do not conclude
"impossible" or "already at the limit". The only acceptable endings are:
(a) a ranked list of levers, each with a measured or bounded expected gain, a card experiment staged for the
lead, and the evidence behind it; and
(b) for any lever you rule out, the specific measurement or primary source that rules it out on this card. A
blog's opinion or "commonly known" does not count.
If the first ideas run out, keep going. Look at each layer below again, combine levers, and read primary
sources: Intel's KNC System Software Developer's Guide and Instruction Set Reference, McCalpin's KNC STREAM
and memory papers and talks, Intel's KNC performance-monitoring and uncore documents, and the MPSS and Linux
memory documentation. Every number you report is either measured on this card by the lead, or cited with a
page or section. Honest negative results are welcome as data. Unsupported pessimism is not.

**Targets.** First verify this card's (7120P) theoretical peak from primary sources: channels, data rate, bus
width, ECC effect. The often quoted 352 GB/s is to be checked, not assumed. The target is 75-85% of the verified
peak, by workload class: read-only, write-only, copy, triad, read-modify-write, and a stencil-like mixed
pattern. Report each class separately; a read-only number is not a triad number.

**What we already know (read first, do not re-derive).**
- `docs/research/knc-characterization.md` C1 (card, 2026-11-10): card-wide write-only streams at 60x4 threads
  reach 83.5 GB/s with `vmovaps`, 114 GB/s with `vmovnraps`, **226 GB/s with `vmovnrngoaps`** plus a fence. So
  writes alone already exceed the folklore ceiling, and the mixed read/write case is where the gap is.
- Same file, line ~480: stream read-modify-write measured at 156.5 GB/s in our energy table.
- `docs/research/knc-best-practice-review.md`: 2 MB pages (McCalpin: STREAM 162 to 175 GB/s), 1 thread per
  core is best for pure streaming (about 10% lost at 4), no `clevict` after streaming stores (tuned STREAM
  gained 10-25% without it).
- 2 MB pages are now available on demand (`/mnt/huge`, `nr_overcommit_hugepages` 4096; CURRENT_STATE card section).
- Our compiler's software prefetch (S8: two-level `vprefetch1`/`vprefetch0`), NGO default for write-only
  streams (E5-08), and the KNC tuning model (ADR-0009, Klemm slides).

**Layers to search (each needs an answer with evidence).**
1. Memory system: GDDR5 channel interleaving and page (row-buffer) policy; read/write turnaround cost and how
   to batch reads and writes per channel; bank conflicts from array placement (offsets between arrays, padding,
   channel hashing); ECC on vs off (bandwidth effect from sources; turning it off is a card configuration
   change the owner decides, so measure-plan it, do not do it).
2. On-die path: the ring, tag directories and address hashing; per-core outstanding misses (fill buffers, L2
   MSHRs) and how many threads and prefetches you need to cover memory latency (Little's law with this card's
   measured latency); how the ring scales at 60 vs 61 cores; core count and placement effects.
3. Software: prefetch distance and type per level (`vprefetch0/1/2`, exclusive `vprefetche*`), prefetch versus
   the hardware L2 streamer, streaming stores (NGO vs NR) and the fence cost, `clevict0/1` use, unrolling, loop
   splitting so each loop has one read stream and one write stream, blocking, and the order in which threads
   touch memory (first touch, interleaved chunks vs contiguous blocks).
4. OS and pages: 2 MB vs 4 KB pages (TLB reach at 240 threads), page coloring if relevant, memory placement
   over channels, transparent huge pages behaviour on MPSS 3.7, and kernel effects on bandwidth runs.
5. Power and clocks: governor, turbo state, memory clock, thermal throttling during long runs; what to record
   so that runs are comparable.
6. What ICC and Intel's tuned STREAM did differently (flags, streaming-store and prefetch defaults), and what
   any paper reached above 180 GB/s on KNC, and how.

**Deliverables.**
1. `docs/research/knc-memory-bandwidth.md`: the verified peak; a lever table (lever, layer, mechanism, expected
   gain with source or bound, risk, cost to try, needs owner approval y/n); the ranked plan; and the compiler or
   runtime changes each winning lever implies for GCC-KNC (for example prefetch distances, store choice, loop
   splitting in the vectorizer, libgomp placement), written as candidate backlog stories.
2. A multithreaded native benchmark `tests/bench/membw/` (C, built with the GCC-KNC prefix, inline asm or our
   builtins where the compiler does not yet emit the instruction) that measures each workload class with each
   lever switchable from the command line: thread count and placement, prefetch distances and types, store
   kind, fence, `clevict`, page size (hugetlbfs at `/mnt/huge`, falling back to 4 KB when unavailable), array
   offsets and padding, chunking, unroll. It uses every CPU it is given (`sched_getaffinity`, one pinned worker
   per CPU, AGENTS.md), runs each case at least 5 times, reports median and range in GB/s with bytes counted the
   STREAM way (and states the counting rule), and checks results so a broken kernel cannot report a fast time.
   A host build passes a small correctness test (`tests/bench/membw/test_*.py`).
3. A staged sweep for the lead: a runner and the exact `card_run --benchmark --threads 240` commands, ordered so
   the cheapest and most likely levers run first, with a time estimate per step and a total under 2 hours for the
   first pass. If performance counters (uncore GBOX or core events via `perf_event_open`) are reachable without
   configuration changes, include a counter mode that shows memory-channel utilization and read/write mix;
   otherwise say exactly what is missing.
4. A short "what we expect" table: for each workload class, today's measured or estimated GB/s, the predicted
   GB/s after the top levers, and the % of verified peak. The lead's card numbers then replace the predictions.

Rules: no card job by the engineer (ADR-0010); the lead runs the sweep in our exclusive card turn. No MPSS,
kernel, module or `/etc` change, and no ECC or clock change: list those as owner decisions with their expected
gain. Vendor documents are read for facts with page references (ADR-0013); write our own code. If you cannot
commit (sandbox), leave changes uncommitted and stop with pm.py ask; the lead commits by hand (owner 2026-11-12).
GCC is not to be rebuilt by you; ask the lead if a compiler change is needed.
