Owner, 2026-11-12: "we need to break through for following up project and it directly impact on fast llm decode can
run on xeon phi". LLM decode streams the model weights once per generated token: per layer, a matrix-vector product
(GEMV) whose matrix is far larger than the caches and whose vector stays resident. So decode speed is read
bandwidth of weight bytes, plus the multiply-add work to consume them.

Same rules as S11-05 and S11-06: find ways up; back every rejected lever with a measurement on this card or a cited
primary source; never conclude "impossible". Read first: `docs/research/knc-memory-bandwidth.md` (S11-05/S11-06
analysis and the corrected long-sample baseline: read 186 GB/s at 120 threads with prefetch 8/64, triad 168, write
170, copy 164, rmw 179; `--mib 2048 --passes 32` is the sample size), `tests/bench/membw/README.md`, and sweep 2's raw
output `.work/_shared/tmp/claude-next23/membw-second.out`.

Deliver:
1. A `gemv` workload in `tests/bench/membw/membw.c` (reuse its threading, placement, pages, prefetch, timing and
   validation machinery): each worker streams its share of a large row-major weight matrix (2 GiB or more in total)
   and accumulates row dot products with a vector that stays in cache (sizes like LLM layers: rows x 4096 and
   x 11008 columns), writing one output per row. Weight formats: fp32; int8 with a per-row (or per-block) fp32 scale,
   expanded in registers; fp16 converted in registers (KNC has `vcvtph2ps`-style up-conversion through the
   load/broadcast path: check the ISA manual and use our builtins or inline asm). Report GB/s of weight bytes and
   effective GFLOP/s, and validate the outputs against a scalar reference.
2. A sweep (`sweep.sh gemv`, under 90 minutes, long samples) that pushes this workload with the levers the read class
   responded to, and more: threads per core 1/2/3/4 with per-thread prefetch distances (L2 far, L1 near), several
   independent weight streams per thread (row interleaving), row blocking so the vector stays in L1, huge pages,
   unroll, and the `vprefetch1`/`vprefetch0` split. Calibration first: the plain read class at the same settings.
3. Analysis in `docs/research/knc-memory-bandwidth.md`: what limits GEMV versus plain read (bandwidth, instruction
   issue, conversion cost for int8/fp16, prefetch coverage), the measured best per weight format, and the
   compiler and runtime stories this implies for GCC-KNC (vectorizer shape for GEMV, prefetch defaults, thread
   density, libgomp placement), as candidate backlog lines. Note what a llama.cpp-style kernel would need.
