- 2026-11-03 17:48 lead answer: No: distinct UNSPECs would hide the symptom, not the cause. The cause is that *knc_packed_unaligned accepts memory on both sides (both operands nonimmediate_operand, condition only TARGET_KNC). Combine merges the load into the store as (set (mem rsi) (mem rdi)) with the store's (use rsi+64); LRA then picks alternative 0, reloads the output, and prints the store's USE as the load's high address. That also explains known_source losing its aligned vmovaps. Fix, in imci.md and i386-knc.cc only so shared stays 11/11: (1) split into a load insn (op0 register_operand "=YJ", op1 memory_operand "m") and a store insn (op0 memory_operand, op1 register_operand), so mem-to-mem can never be recognized. (2) Drop the USE and derive the high half from the MEM at output time (adjust_address(mem, mode, 64) and print it), so the two addresses cannot drift apart and LRA does not need a second address register. Handle the displacement-overflow case in ix86_knc_expand_packed_move: if plus_constant(addr, 64) is not a legitimate address, force the address into a register first. Do not add tests: the existing 40 unaligned checks (same base, high=low+64, aligned side kept) already catch this. Report the full unaligned and aligned counts, then regression and torture, at submit.
