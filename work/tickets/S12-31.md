Owner, 2026-11-14: GCC-KNC must always be faster than GCC 5.1.1. HPCG is the one development program that is
slower: S11-28 fixed-work pilot, serial, rating 0.0845-0.0847 vs 0.0860-0.0863 GFLOP/s (about 1.8%, all six pairs,
all three profiles; docs/research/m4-baseline.md "Primary pilot observations", `.work/_shared/S11-28/results.jsonl`).
HPCG had no qualified profile in S11-15, so the cause is unknown.

Troubleshoot (Fable): compare GCC-KNC and GCC 5.1.1 code for HPCG's hot kernels at the S11-18 build flags
(ComputeSPMV_ref, ComputeSYMGS_ref, ComputeDotProduct_ref, ComputeWAXPBY_ref, ComputeMG/restriction/prolongation),
using the installed prefix and the donor toolchain; find which kernel loses and why (scheduling, spills, address
arithmetic, imul cost, prefetch choice, vectorization or the lack of it, code size, call overhead, libm). Use S12-19's
vec_triage on an HPCG -g build and a short card profile run (lead runs it; under 20 minutes, S11-28 fixed-work input)
if static comparison is not enough. Then fix it in general (keyed on code properties, never on HPCG names), strict FP,
red-then-green T1 tests, T0-T2, ICE sweeps, x86 identity (lead); stage a paired HPCG A/B (S11-28 fixed work, two
pairs per profile, full/3100/5100) plus two controls. Coordinate with S12-30 (sparse SpMV) and S12-21 (imul cost):
if one of those is the cause, say so and fold the fix there instead of duplicating it.

Phase 1 runs on lane corpus3 with the installed prefix (no GCC tree); the lead moves the ticket to a GCC lane for the implementation.
